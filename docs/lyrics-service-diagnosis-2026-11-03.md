# 歌词服务不可用诊断（2026-11-03）

## 结论

本次故障的直接原因是 LRCLIB 对部分歌词查询返回 HTTP 503，错误名为 `ServerOverloaded`。Windows 经系统代理、Windows 禁用代理直连，以及 WSL 的独立请求都收到相同错误，因此本次失败不能归因于系统代理。蓝牙与歌曲读取正常。

故障具有暂时性和查询差异：同一时段部分查询成功，部分查询失败，不能据此认定 LRCLIB 全站不可用。客户端无法确认服务端内部负载或具体查询失败的内部原因。

诊断期间程序随后成功加载《Señorita》的 57 行同步歌词；切换到《Smells Like Me》后成功加载 53 行同步歌词。软件保持运行，iPhone 的 Apple Music 连接正常。

## 复现与实测

使用 `python3 desktop/run.py` 启动真实 Windows WPF 软件，日志出现：

```text
AMS: Connected r1 iPhone 已连接，等待播放信息。
AMS: Snapshot r1 正在播放
LYRICS_ERROR: 歌词服务暂时不可用。
```

窗口显示当前歌曲《Señorita》，歌手 `Shawn Mendes & Camila Cabello`，并提示歌词服务不可用及自动重试。设备标识未保存。

连续两次执行现有网络检查：

```sh
python3 desktop/run.py --check-lyrics
```

两次均先成功收到《夜的第七章》的 13 条同步歌词候选，随后在视频标题的查询路径抛出“歌词服务暂时不可用”，退出码为 1。

使用 Windows .NET Framework `HttpClient`、TLS 1.2、`LyricConnector/0.1` User-Agent，对请求逐个验证：

| 查询 | HTTP 状态 | 结果 |
| --- | --- | --- |
| `/api/search`：`Señorita` + `Shawn Mendes & Camila Cabello` | 503 | `ServerOverloaded` |
| `/api/search`：仅 `Señorita` | 200 | 20 条候选，包含 Shawn Mendes / Camila Cabello 的同步歌词 |
| `/api/search`：`夜的第七章` + `Jay Chou` | 200 | 13 条候选 |
| `/api/search`：`止戰之殤` + `周杰倫` | 503 | `ServerOverloaded` |
| `/api/get`：`Señorita` + 双歌手 + `duration=192`，未带专辑 | 503 | `ServerOverloaded` |

最后一项是用于缩小问题的请求，不声称与软件当时发送的完整精确查询完全一致。

503 的响应为：

```json
{"message":"The server is busy, please retry in a moment","name":"ServerOverloaded","statusCode":503}
```

响应还包含 `Retry-After: 1`。Windows 代理与直连的同一“歌名＋歌手”搜索分别约 1.32 秒、1.48 秒返回 503；WSL 同一搜索也返回 503。它们是明确的 HTTP 错误响应，而非本次客户端 20 秒超时。

[LRCLIB 官方错误说明](https://lrclib.net/docs#errors)将 503 / `ServerOverloaded` 定义为服务暂时繁忙，要求按 `Retry-After` 等待后重试；429 则是另列的请求限流错误。本次捕获的是 503，不能将其直接判定为客户端触发 429 限流。

## 客户端为何显示统一的不可用提示

- `desktop/LyricsStore.cs` 的 `GetAsync` 将 429 和所有 5xx 转换为同一个 `HttpRequestException("歌词服务暂时不可用。")`，丢失了状态码、响应错误名及重试头，因此现有日志无法直接区分限流和服务端繁忙。
- `SearchAsync` 仅在“歌名＋歌手”查询成功但结果为空时，继续执行仅歌名查询。首次请求抛出 503 时，整次操作立即中止，即使仅歌名的请求当时可用也不会执行。
- `desktop/Windows.cs` 已提供 10、20、40 秒的三次自动重试；未读取服务端的 `Retry-After`。本次 `Retry-After` 为 1 秒，现有等待时间更长，但不能保证服务在下次请求时已经恢复。

## 验证与范围

`python3 desktop/run.py --test`：85 项检查全部通过。没有运行前端生产构建。本次仅诊断，没有修改业务代码，没有新增自动降级行为。

计划验证界面“清空歌手、仅搜歌名”时，检测到手机已切换歌曲，因此未修改检索框、未提交搜索，也未手动替换歌词；仅歌名路径的可用性已通过独立 HTTP 请求验证。随后读取真实窗口，显示《Smells Like Me》、Charlie Puth、`LRCLIB · 53 行同步歌词`。

后续若改进客户端，优先保留 HTTP 状态、服务端错误类型与 `Retry-After`，让日志能区分服务端繁忙与限流。是否在服务错误后扩展搜索应作为明确的产品行为决定，避免无条件扩大请求量。外部服务的间歇故障无法仅通过本地测试保证永久消除。

## 自动搜索与手动搜索复核（统一前）

同日进一步对比实际调用路径：

| 行为 | 自动搜索 `FindAsync` | 手动搜索 `SearchAsync` |
| --- | --- | --- |
| 本地缓存 | 命中后直接采用，不访问服务 | 受支持的播放器直接重新在线搜索 |
| 精确查询 | 未推断标题、歌手非空且时长有效时，先访问 `/api/get`，携带原始歌名、歌手、时长和可用的专辑 | 不访问 `/api/get` |
| 候选搜索 | 必要时调用 `/api/search`，使用推断后的歌名、歌手 | 调用 `/api/search`，使用输入框中的歌名、歌手 |
| 仅歌名搜索 | 歌名＋歌手成功返回空结果时执行 | 相同 |
| 扩展搜索 | 未发现直接匹配的同步歌词时，可能按专辑和歌手继续查询 | 不执行 |
| 候选排序 | 进入候选路径后使用 `LyricMatcher.Rank`；缓存和精确查询直接采用的结果不经过该排序 | 使用 `LyricMatcher.Rank` |
| 服务错误与超时重试 | 等待 10、20、40 秒，最多重试三次 | 相同 |

两条路径共用同一个 `HttpClient`、User-Agent 和错误处理。请求中没有标识“自动”或“手动”的模式参数。自动查询由歌曲快照变化触发，播放进度更新不会重复触发查询。未命中缓存时，自动路径单轮最多有五个顺序 HTTP 请求，手动路径最多两个；遇到服务错误则立即停止后续步骤。

为验证路径差异，在独立 Windows PowerShell 进程中加载项目真实的 `Core.cs`、`SongQuery.cs`、`LyricsStore.cs`，只在内存中的源码副本添加请求路径和 HTTP 状态输出。使用临时空缓存，每个请求前等待 300 毫秒，依次调用真实的 `FindAsync` 和 `SearchAsync`。临时目录测试后删除，项目业务代码及用户缓存未修改。

首轮结果：

| 歌曲与参数 | 自动路径 | 手动路径 |
| --- | --- | --- |
| 《十面埋伏》、`Eason Chan`、`duration=232` | 首个 `/api/get` 返回 503，约 2.03 秒失败 | `/api/search` 返回 200，共 17 条候选，其中 16 条有同步歌词，约 2.25 秒完成 |
| 《Señorita》、`Shawn Mendes & Camila Cabello`、`duration=192` | 首个 `/api/get` 返回 503，约 1.18 秒失败 | `/api/search` 返回 200，共 20 条同步歌词候选，约 0.94 秒完成 |

两首歌均省略专辑以构造最小场景；手动搜索不传时长。它们用于复现真实方法的请求差异，不是对运行中程序完整请求的抓包。503 响应均为 `ServerOverloaded`，带 `Retry-After: 1`。

随后使用相同 Windows HTTP 客户端设置，对《十面埋伏》按 `/api/search`、`/api/get`、`/api/search` 顺序补测，三次均返回相同的 503。因此，首轮“自动失败、手动成功”不能被解释为 `/api/search` 始终可用，也不能单凭调用顺序排除服务随时间变化。

可以确认自动路径存在额外失败点：精确查询返回 503 时，候选搜索还没有执行；扩展查询返回 503 时，前面已得到的候选也不会返回给界面。但没有服务端指标或限流证据证明本客户端的自动搜索造成了服务器过载。本次记录的错误是 503，而不是明确表示客户端限流的 429。

如果统一两种模式，可让自动查询在缓存未命中时使用与手动搜索相同的候选搜索入口，再统一排序与选择，减少模式之间的接口差异。这是后续改动建议，本轮只做诊断，未修改业务代码，也未运行前端生产构建。

## 统一搜索流程后的修复

后续按上述建议修改了搜索流程。自动查询仍先读取缓存，未命中后调用与手动搜索相同的 `SearchAsync(Track, title, artist, cancellation)`。该方法负责候选查询和同步歌词优先排序，两种模式由界面使用同一段逻辑自动应用候选。

已删除 `/api/get` 精确查询、专辑 / 歌手关键词扩展查询、相关私有方法以及扩展搜索状态。每轮在线查询先提交歌名和歌手，成功返回空结果时再仅提交歌名，最多两个顺序请求。专辑和时长继续用于本地评分，既有缓存选择和本地歌词导入保持有效。

针对性回归使用模拟 HTTP 响应：候选接口正常，其他接口返回 503。改动前自动查询在精确接口失败，改动后自动和手动发出相同的候选请求、返回相同的排序结果。还覆盖了缓存命中不联网、手动搜索绕过缓存、标题提取、空结果后仅搜歌名、纯文本结果不扩展搜索，以及没有结果时正常结束。`python3 desktop/run.py --test` 共 107 项检查通过。

`python3 desktop/run.py --check-lyrics` 的公网检查仍在访问候选接口时收到“歌词服务暂时不可用”。因此，不能将本地回归通过解释为 LRCLIB 已恢复；本次修复消除的是自动搜索独有的请求路径。未运行前端生产构建。

使用修改后的源码重启程序，已重新连接 iPhone。运行日志先出现一次 `LYRICS_ERROR: 歌词服务暂时不可用。`，随后出现 `LYRICS: LRCLIB · 100 行同步歌词`，表明新流程能够获取同步歌词，服务可用性仍有波动。
